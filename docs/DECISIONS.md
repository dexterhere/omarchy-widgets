- 2026-10-23 AUTH-MODE Default unlock mode is "convenient": the vault key is released to the daemon at login through the Secret Service keyring, passphrase kept as recovery, "strict" (passphrase every login) selectable. - 2026-10-23 AUTH-UNLOCK Daemon-side vault unlock, passphrase mode only. Design: `ow vault unlock` prompts without echo and sends the passphrase once as hex in a `vault.unlock` frame over the 0600 same-uid socket; `owd` calls `Vault::open`, keeps the `Vault` (zeroizing keys and records) until `vault.lock`, the idle timeout or exit, and hands providers a `SecretHandle` (see TRAIT). Admin ops are same-uid only (SO_PEERCRED) and a frame that mixes an admin op with a `widget` field is refused (`denied`, audited by op name); D-1 stays open. `ow` refuses to send anything unless the socket directory is private and ours and the peer uid is ours. Constants: 5 free failures, lockout 30 s doubling to 15 min, one attempt at a time, idle lock 15 min measured from the last secret resolved, so a polling widget keeps it open (an absolute timeout would force an unlock every 15 minutes); counters are in memory and reset on daemon restart. Wrong passphrase, missing, unreadable or corrupt vault all answer `denied`; lockout and a concurrent attempt answer `rate_limited`. Hex was chosen so the passphrase is arbitrary bytes with no JSON escapes, and it is decoded outside serde's tagged/flattened buffering; frame buffers are wiped after use. `ow vault set`: passphrase from `/dev/tty`, value from stdin; no terminal means a clear failure; `--passphrase-stdin` is the explicit alternative. Added `zeroize` to `ow-proto`, `ow-core` and `owd` and `ow-vault` to `owd`; no new crate in the lockfile. Residual risk: any same-uid process can try passphrases, bounded by the lockout (a restart of the daemon resets it); the passphrase crosses the socket once; memory is non-dumpable but readable by root, there is no `mlock`, swap is possible; while unlocked, every record is decrypted in the daemon, and after unlock "any process running as you could ask the daemon for what grants allow" (D-1); a wrong-vs-missing vault differs in timing (Argon2 runs only if the file opens). Not done: keyring/Secret Service auto-unlock (spike S4), network providers and the egress wrapper, grants admin ops, config binding of providers to secrets, automatic reload after `ow vault set|remove` (only lock and a fresh unlock purge caches), different-uid refusal tests. Evidence: crates/owd/src/unlock.rs, crates/owd/tests/unlock.rs, crates/owd/tests/leak.rs (mutation-checked), crates/ow/tests/. Would change: spike S4 gives a safer key release, or D-1 introduces per-widget identity.
- 2026-10-23 AUTH-UNLOCK follow-up (independent review fixes and deliberate omissions). Fixed: idle and lockout timing now use CLOCK_BOOTTIME (monotonic time stops in suspend); `ow vault set|remove|rotate|wipe` lock the daemon afterwards; `"widget":null` counts as a widget claim; lock plus purge are atomic under the hub state lock and every release is gated on a key epoch; in-flight workers have their own counter; unlock fails closed if its audit line cannot be written; admin-shaped denials are rate limited before the grant lookup; secret handles borrow the fetch context and are built only in `ow-core` (closure API preferred); the prompt refuses Ctrl-D/U/W; one private-directory check. Deliberately NOT done now, each a possible later step: (1) narrowing memory: open the vault read-only and drop the master key after unlock, keep only the records named by `provider.secrets()`, or decrypt per fetch; today every record and both keys stay resident while unlocked; (2) `mlockall` or an encrypted-swap requirement: pages can reach swap; (3) an absolute maximum session length: a polling widget keeps the vault open indefinitely by design; (4) locking on screen lock or suspend through logind: the boottime idle timer only locks after the idle time has passed. Also open: a snapshot reply that passed its last epoch check can still reach a client just after a lock on another connection, and a different-uid peer test needs a second uid. Would change: spike S4 and D-1 outcomes, or a user report that the 15-minute idle rule is wrong for them.
- 2026-10-23 AUTH-HTTP The egress crate `crates/ow-egress` uses `ureq` 3.5.0 (pinned `=3.5.0`, `default-features = false, features = ["rustls"]`; no `gzip`, `brotli`, `cookies`, `json`, `charset`, `socks-proxy`, `native-tls`, `platform-verifier`) on `rustls` 0.23.46 with the `ring` provider. Why ureq: blocking API matches the synchronous `Provider` trait, no async runtime enters the tree, redirects/proxy/timeouts/body limits are config switches, and we write no HTTP parser (AUTH-DEPS). Maintenance evidence: crates.io facts checked by Dexter today (ureq 3.5.0 updated 2026-10-21, rustls 0.23.46, ring 0.17.14 last released 2025-03, aws-lc-rs 1.18.2, webpki-roots 1.0.11, rustls-native-certs 0.8.5); I confirmed that the pinned versions resolve and that `cargo audit` (advisory DB of 1350 entries, loaded 2026-10-23) reports nothing for them. I did not independently check release dates or maintainer activity. Full tree: 28 runtime crates besides `ow-egress` (3 more build-time helpers for ring: `cc`, `shlex`, `find-msvc-tools`), 37 with dev-dependencies (`rcgen` and `rustls` for the test server). No OpenSSL, native-tls or tokio. Licenses: all inside the allow-list except `webpki-roots` (CDLA-Permissive-2.0, the Mozilla root data); that one identifier is added to `deny.toml`, nothing else. Crypto provider: `ring`, not `aws-lc-rs`: it is what ureq's `rustls` feature already selects, needs no cmake or NASM, and has the smaller tree; cost: ring's last release is 2025-03 (about 19 months), so we depend on advisories being published and acted on. Trust roots: DEVIATION from AUTH-EGRESS ("system roots"): the compiled-in `webpki-roots` bundle. Reason: `rustls-native-certs` (and the platform verifier on Linux) honour `SSL_CERT_FILE` and `SSL_CERT_DIR`, so an environment variable set for the daemon would be a custom-CA backdoor, which this crate must not have; the bundle also does not depend on user-writable trust files and adds no crates. Cost: CA removals reach users only with a daemon update, and a corporate TLS-inspection CA is not trusted (requests fail closed with `Tls`, which is the safe direction). Logging: ureq and rustls call `log::debug!` with URIs and responses. `ow-egress` depends on `log` only to set its `max_level_off` feature, which compiles every log macro in the whole binary to nothing, and a test asserts `log::STATIC_MAX_LEVEL == Off`; no logger exists in the workspace either way. Residual risk: the library copies the `Authorization` header value into its own buffers (`http::HeaderValue`, connection write buffers) that `Zeroizing` cannot reach, we mark the value sensitive but cannot wipe those copies; a same-uid process can read daemon memory unless the process is non-dumpable (it is) and ptrace is restricted; `ring` contains C and assembly; no certificate pinning (decided in AUTH-EGRESS), so any CA in the Mozilla bundle can issue for an allow-listed host; DNS is trusted only through TLS verification. Not verified locally: `cargo deny` (not installed); the real handshake against a real provider host (tests use a local server with a test root). Consequences of the bundled roots: they are frozen at build time, so a CA that is later distrusted stays trusted until a daemon update ships; there is no revocation checking (no OCSP or CRL), so a revoked leaf certificate is accepted; any CA in the bundle can issue a certificate for an allow-listed host and there is no pinning; a corporate or local CA fails closed with no escape hatch; distribution security updates do not cover the bundle. Would change: an advisory on ring or ureq that is not fixed within days, ureq dropping the ring provider, a vetted need for system roots (then add an explicit user config, never an environment variable), or an out-of-process network helper replacing the in-process module.

- 2026-10-23 DEP-TIME `jiff` 0.2.38 (default features off; `std`, `tz-system`, `tzdb-zoneinfo`) added to `ow-providers` for `system.time` (local time and zone abbreviation). std has no local-time support.
